# ADR-0006: Git-Based Task Management System

## Status

Accepted

## Context

Maslow is designed for multi-agent collaboration on codebases. Humans need a mechanism to inject work into the project and have agents discover, claim, and execute that work. The system must work across multiple clones of the repository (different machines, different agents) without centralized coordination.

Key constraints:
- Git is the only shared infrastructure; no external task tracker or database
- Agents should not need to read entire task descriptions to determine relevance
- Multiple agents on different clones must not duplicate work
- Humans need a draft state to iterate on task descriptions before releasing to agents
- The mechanism must be propagated into new projects via `maslow scaffold`

## Decision

Tasks are stored as markdown files with YAML frontmatter in `docs/tasks/`. The frontmatter contains all metadata needed for agent decision-making (status, priority, assignment, dependencies, tags). The body contains the full requirements.

### Format

Files are named `<id>_<SLUG>.md`. Frontmatter fields: `id`, `title`, `status`, `priority`, `created`, `updated`, `assigned_to`, `assigned_at`, `depends_on`, `tags`.

### Status Lifecycle

`draft` -> `todo` -> `in_progress` -> `done` (with `blocked` as a side state)

Humans control the `draft` -> `todo` transition. Agents control `todo` -> `in_progress` -> `done`.

### Multi-Agent Claiming Protocol

Agents claim tasks by updating frontmatter, committing, and pushing. If push fails due to a conflict, the agent pulls and checks whether someone else claimed the task. This uses git's native conflict detection as a distributed lock mechanism.

### Convention File

`docs/tasks/CONVENTION.md` is the authoritative reference for the format, lifecycle, and protocol. It is generated by `maslow scaffold` for new projects.

## Alternatives Considered

1. **GitHub Issues / External tracker**: Rejected because it introduces a dependency outside git and is not available in all environments (offline, different forges, etc.)

2. **Single TASKS.md file**: Rejected because concurrent edits by multiple agents would cause frequent merge conflicts, and frontmatter scanning would not work.

3. **YAML/JSON task database**: Rejected because it sacrifices human readability and markdown body authoring. The frontmatter-in-markdown approach gives the best of both worlds.

4. **Branch-per-task claiming**: Rejected as overly complex. The commit-and-push protocol is simpler and leverages existing git workflows.

## Consequences

### Positive

- Zero external dependencies — works anywhere git works
- Human-friendly authoring (markdown + frontmatter)
- Agent-efficient scanning (frontmatter-only reads)
- Natural audit trail via git history
- Propagated into scaffolded projects automatically

### Negative

- Claiming protocol is best-effort, not perfectly atomic (brief race window between read and push)
- Task discovery requires scanning multiple files (mitigated by frontmatter-only reads)
- No real-time notification when new tasks are added (agents must poll via git pull)

### Mitigations

- The race window is small in practice — an agent must read, modify, commit, and push, and the first to push wins
- If duplicate work does occur, git history makes it visible and recoverable
- Agents are instructed to always pull before claiming
